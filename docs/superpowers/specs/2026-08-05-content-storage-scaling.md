# 콘텐츠 저장 방식 — 언제 JSON을 벗어나야 하는가

작성일: 2026-08-05

## 이 문서의 목적

지금 콘텐츠는 `data/<책>.json` 9개 파일에 있고 앱에 통째로 박혀 나간다. 목표는 **100권 × 300~400개**다.
그 규모에서 지금 방식이 버티는지 따져 보고, 못 버틴다면 **언제 · 어디로 · 무엇을 조심하며** 옮길지 적어 둔다.

지금 당장 무언가를 바꾸기 위한 문서가 아니다. 나중에 옮길 때 "왜 옮기는지"를 처음부터 다시 따지지 않기 위한 기록이다.

## 결론

**지금 방식 그대로 간다. 다만 8권쯤 채워질 때(약 2,500~3,000개 항목) Firestore로 옮긴다.**

## 측정 — 추측이 아니라 실제 데이터

2026-08-05 기준 `data/` 전체를 잰 값이다.

| 파일 | 크기 | 항목 수 | 항목당 |
|---|---|---|---|
| english.json | 7KB | 4 | 1,891B |
| hanja.json | 10KB | 6 | 1,759B |
| hanmun.json | 13KB | 6 | 2,206B |
| latin.json | 16KB | 12 | 1,354B |
| liberal.json | 3KB | 1 | 2,740B |
| psychology.json | 18KB | 10 | 1,850B |
| quote.json | 25KB | 18 | 1,423B |
| tracks.json | 16KB | 6 | 2,700B |
| writing.json | 24KB | 12 | 2,023B |
| **합계** | **132KB** | **75** | **평균 1,799B** |

이 값으로 목표 규모를 환산하면:

```
100권 × 350개 = 35,000개 항목
35,000 × 1,799B ≈ 60MB
본문이 지금의 2배로 길어지면 ≈ 120MB
```

**이 60MB는 순수 텍스트만이다.** 이미지와 음원은 이미 Firebase Storage에 있고 앱에 들어가지 않는다.

## 왜 그 규모에서 안 되는가

### 1. 앱을 켤 때 100권이 전부 메모리에 올라간다

`lib/*.ts` 9개가 모두 정적 `import`를 쓴다.

```ts
import tracksData from '@/data/tracks.json';   // 9개 파일 전부 이 방식
```

정적 import는 앱 시작 시점에 평가된다. 사용자가 1월 1일 한 항목만 보려 해도 100권이 다 로딩된다.
60MB JSON을 파싱하면 자바스크립트 객체로는 **150~250MB 메모리**를 쓴다. 중저가 안드로이드에서 앱이 죽는다.

### 2. 앱 용량이 그만큼 늘어난다

콘텐츠가 앱 바이너리에 포함되므로 내려받는 용량이 60MB 늘어난다. 첫 설치 장벽이 된다.

### 3. 오타 하나 고치려고 앱을 새로 배포해야 한다 — 이게 제일 크다

35,000개를 사람이 쓰면 오타와 사실 오류는 반드시 나온다. 지금 구조에서는 글자 하나를 고쳐도
빌드 → 스토어 심사 → 사용자 업데이트를 거쳐야 하고, 심사에만 며칠이 걸린다.

용량과 메모리는 기술로 우회할 여지가 있지만(뒤에 나오는 지연 로딩), **이 문제는 저장 위치를 옮기지 않으면 풀리지 않는다.**

## 언제 옮기는가

체감되기 시작하는 지점은 대략 **2,500~3,000개 항목 — 8권 정도를 다 채웠을 때**다.
그 무렵부터 앱 켜는 속도가 눈에 띄게 느려진다.

지금(75개)은 아무 문제 없다. 편집도 JSON이 가장 쉽다. **미리 옮기지 않는다.**

## 어디로 — Firestore

**Firebase가 이미 이 프로젝트에 붙어 있다.** `lib/firebase.ts`가 Storage(이미지·음원)를 쓰고 있으므로
같은 프로젝트에서 Firestore를 켜면 된다. 새 서비스를 고르거나 계정을 만들 필요가 없다.

옮긴 뒤의 모습:

- 앱은 **오늘 볼 항목만** 받는다 (약 1.8KB)
- 콘텐츠 수정이 **앱 배포 없이** 즉시 반영된다
- 받은 항목은 기기에 캐시해 오프라인에서도 보인다

### 검토했지만 충분하지 않은 대안 — 책별 지연 로딩

정적 import 대신 그 책을 열 때만 `require()`하면 시작 속도와 메모리는 크게 나아진다.
하지만 **앱 용량(문제 2)과 배포 없는 수정(문제 3)은 그대로다.** 임시방편은 되어도 답은 아니다.

## 옮길 때 무엇이 싸고 무엇이 비싼가

### 싼 쪽 — 화면 코드는 바뀌지 않는다

화면은 데이터 파일을 직접 보지 않는다.

```
화면 → getBookLesson(bookId, lessonId) → lib/classic.ts → tracks.json
                                          ↑ 여기만 바꾸면 된다
```

`lib/classic.ts`는 43줄짜리 얇은 접근자다. JSON 대신 Firestore를 읽게 바꾸는 일은 이 파일 9개에서 끝난다.

### 비싼 쪽 — 동기에서 비동기로 바뀐다

지금 조회 함수는 모두 동기다.

```ts
export function getTracks(): Track[]        // 즉시 반환
export function getBookLesson(bookId, lessonId): BookLesson | undefined
export function getBookCalendar(bookId): CalendarDay[]
export function findLesson(lessonId): BookLesson | undefined
```

서버에서 받아오면 비동기가 되고, 이 함수들을 렌더 중에 바로 쓰는 화면들이 **로딩 상태를 다뤄야 한다.**
파일 9개로 끝나지 않고 화면도 손대야 한다.

**그렇다고 지금 미리 비동기로 바꾸지는 않는다.** 데이터가 즉시 있는데 로딩 상태를 만들면 코드만 복잡해진다.
옮기는 시점에 한 번에 하는 편이 낫다.

## 옮길 때 확인할 것

1. `data/*.json`을 Firestore 컬렉션으로 올린다. 책 하나가 컬렉션 하나, 항목 하나가 문서 하나.
2. `lib/<책>.ts` 9개를 Firestore 조회로 바꾼다. **화면은 건드리지 않는다.**
3. 동기 → 비동기 전환에 따른 로딩 상태를 화면에 넣는다. 여기가 실제 작업량이다.
4. 오프라인 캐시를 켠다. 지하철에서도 오늘 항목이 보여야 한다.
5. 목차(365일)는 항목 전체가 아니라 **표제만** 받아 오도록 나눈다 — 목차 때문에 한 책을 통째로
   받으면 옮긴 의미가 없다. `lib/books.ts`의 `getBookCalendar`가 이 부분이다.
6. `findLesson`은 보관함이 책을 모르는 항목 id로 찾을 때 쓴다. 지금은 9권을 순회하는데,
   원격에서는 순회가 비싸다. 항목 id에 책 접두사가 있으므로(`classic_1_polka`) 그것으로 바로 찾게 바꾼다.

## 지금 하지 않는 것

- Firestore 도입 — 8권째까지 미룬다
- 조회 함수의 비동기 전환 — 위와 함께 한다
- 책별 지연 로딩 — 근본 문제를 풀지 못해 채택하지 않는다
